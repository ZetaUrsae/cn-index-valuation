## 三、工程架构评估

**结构（10 步单入口管线，README 有完整表格）：**

```
run_weekly.py（单入口，ASOF 可回补）
 ├─ 取数层：fetch.py → fetch2b.py → fetch3.py → meta.py → fetch_yield_tail.py
 ├─ 计算层：process.py → tech.py → proc2.py → prep.py
 └─ 组装层：gen2.py（work/*.json + data2.json → 注入 template2.html）
```

**做得好的设计（建议保留）：**

1. **增量缓存体系**：`raw.json`/`etf_raw.json`（15 天重叠窗口）、`pcr_raw.csv`（1 个月）、`yield10y_history.json`（400 条尾部），均按日期合并去重、新值优先，可安全重跑——大幅降低 Tushare 积分消耗。
2. **fail-fast**：任一步非零退出即中断，不产出半成品报告；数据文件在末尾一次性落盘，中途失败不污染历史库（`fetch.py`/`fetch3.py` 尤其明显）。
3. **非致命隔离**：`fetch_yield_tail.py` 恒以 exit 0 退出，10Y 补齐失败只告警——与提示词"10Y 失败不影响出报告"口径一致。
4. **模板注入**：`template2.html` 全库唯一 `/*__DATA__*/` 占位符（第 301 行，已验证唯一），`replace` 安全。
5. **配置集中**：`cfg.py` 统一管路径、ASOF 推导、Tushare 连接，大部分脚本复用。
6. **文档与记忆**：README 数据缓存说明详尽；自动化 memory 保留历次运行指标快照，可复核。

**架构层面的小瑕疵：**

- 路径硬编码不统一：`proc2.py`/`tech.py`/`prep.py`/`gen.py`/`reorder.py` 直接写死绝对路径，未复用 `cfg.BASE`（P3-2）。
- `cfg.py` 在 import 时即调用 Tushare `trade_cal` 推导 ASOF——10 个子脚本每次启动各一次 API 调用（每天约 10 次），且接口抖动会直接让 import 崩溃（P3-1）。

## 四、代码稳健性（问题分级）

### P1 · 需尽快修复

**P1-1 `fetch2b.py` 合约缓存 TTL 回退（PCR 漏算复发风险）**

- 现状：`scripts/fetch2b.py:26` 为 `if age <= 20`；而 10-17 修复后的版本（`.workbuddy/tmp/backup_20261019/fetch2b.py`）是 `age <= 4`。10-19 目录重组时误用了更早的旧版，**10-17 的修复被回退**。
- 背景：ETF 期权每月第 4 个周三后新系列上市。TTL=21 天时曾导致 10-14/15/16 三天 PCR 漏算 72 份新合约、数值系统性偏低（300 0.742→0.776、创业板 0.369→0.476），当时已修复并记录在案。
- 影响：TTL=20 天下，新合约上市后最长 20 天内 PCR 持续漏算。当前 opt_contracts.json 的 fetched=10-17，尚在缓存期内未暴露，但下月新系列上市即触发。
- 修复：`age <= 20` 改回 `age <= 4`（日报场景每天跑，4 天 TTL 足够覆盖），并删除或隔离 `backup_20261019/` 避免再次误取。

**P1-2 提示词第 2 步与第 3 步顺序不合理（实际流程与字面流程相反）**

- 现状：提示词要求"第 2 步先联网更新 manual_inputs.json 三项（含机构观点 views/syn）→ 第 3 步再跑管线"。
- 问题：`views`/`syn` 需要引用管线产出的最新指标（PE 分位、ETF 份额变化、PCR 分位、回撤），在全量跑之前写必然基于旧数据。实际执行记录（10-16 经验 6、10-20 运行）都是"先跑管线拿指标 → 据实重写 views/syn → 单独重跑 gen2"。
- 修复：提示词第 2 步拆为"先跑管线前可更新的部分（bond10y 可查则查）"+"跑完管线后据新指标重写 views/syn 并单独重跑 gen2.py"，或直接按实际可行顺序重排为：管线 → 据实更新人工项 → 重跑 gen2 → 自检。

### P2 · 建议排期修复

**P2-1 `proc2.py:84` 硬编码 `"20260101"`（YTD 基准定时炸弹）**

- ETF 份额 YTD 以 `x < "20260101"` 的最后一个点（2026-12-31 收盘份额）为基准。2027 年内运行仍恰好正确；**2028 年起 YTD 会错误地继续以 2026 年底为基准**。
- 修复：改为动态 `ASOF[:4] + "0101"`，与 `process.py` 的 YTD 计算保持一致。

**P2-2 `fetch2b.py` 吞异常后仍写盘（数据截断风险）**

- `opt_daily` 分页异常被 `except` 吞掉仅打印 ERR，随后照常执行 `old = old[old["date"] < ms[0][0]]` 截断旧数据并写回 `pcr_raw.csv`。若整月抓取失败，该月旧数据被丢、新数据没进来，形成数据空洞，直到下次成功重跑才恢复。
- 对比：`fetch.py`/`fetch3.py` 异常直接崩溃不落盘，更安全。两种失败模式不一致。
- 修复：抓取失败时保留旧文件原样退出（或 exit 非零），把"写坏数据"变成"不写数据"。

**P2-3 `gen2.py:129` `DIV[code]` 直接索引（人工文件缺 key 即崩）**

- `manual_inputs.json` 若被误编辑缺某指数 div，`gen2.py` KeyError、整条管线中断。改 `DIV.get(code)` 并在报告中显示"—"更稳（提示词已要求"拿不到的数据不编造，保持原值"）。

5. **第 4 步自检清单偏薄**。自动化 memory 里已积累成熟校验手法但未固化进提示词，建议补入：
