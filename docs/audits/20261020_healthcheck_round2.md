## 二、工程架构评估

### 2.1 结构（实测）

```
run_weekly.py  ← 单入口，ASOF 由 cfg 推导，可通过环境变量回补
├─ 取数层  fetch.py(增量) → fetch2b.py(PCR增量+合约缓存) → fetch3.py(增量) → meta.py → fetch_yield_tail.py(非致命)
├─ 计算层  process.py(估值分位/涨跌) → tech.py(均线/回撤) → proc2.py(PCR/份额) → prep.py(60日K线)
└─ 组装层  gen2.py  work/*.json + manual_inputs.json → DATA → 注入 template2.html
```

### 2.2 做得好的地方（建议保留）

1. **增量缓存体系一致**：`fetch/fetch3` 用 15 天重叠窗口按 trade_date 合并去重、新值优先；`fetch2b` 用 1 个月、`fetch_yield_tail` 用 400 条尾部。全部可安全重跑，显著节省 Tushare 积分。这是本项目最有价值的设计。
2. **fail-fast**：任一步非零退出即 break，不产出半成品。
3. **非致命步骤隔离**：`fetch_yield_tail.py` 恒 `sys.exit(0)`，10Y 失败只告警——与提示词"10Y 失败不影响出报告"一致。
4. **模板占位符唯一**：`/*__DATA__*/` 全文件仅 1 处，`str.replace` 注入安全。
5. **配置集中**：`cfg.py` 统一 BASE/DATA/WORK/REPORTS/ASOF/pro_api，路径不散落（`baseline` 比预期好，见 P3-1）。

### 2.3 架构层面的问题

- **A-1 目录语义漂移（P3）**：注释与 README 说 `work/` 是"每次运行可清理的中间产物"，但 `recompute_sharpe.py` 依赖 `work/backtest_erp_result.json`，而该文件实际已迁往 `erp_backtest/work/`——这个脚本在当前目录结构下**必然 FileNotFoundError**。同时 `work/` 里躺着两个 1.4MB 的临时 JS（`_inline_check.js`、`_smoke_runner.js`），是从没被清理过的验证产物。
- **A-2 废弃脚本与现役脚本混放（P3）**：`gen.py`（旧版生成器，内部写死 `BOND10Y = 1.6654` 和旧股息率）、`template.html`、`reorder.py`（一次性改版式工具）与现役 10 步管线同处 `scripts/`。`reorder.py` 尤其危险——它按 12 个 `<!-- 注释 -->` 锚点重排 template2.html，一旦有人运行而模板已改动，轻则 assert 失败，重则部分重排。
- **A-3 逻辑重复（P2）**：`fetch.py` 与 `fetch3.py` 各自实现了一份完全相同的 `norm()` + `merge()`；YTD 基准在 `process.py` 和 `proc2.py` 里各写了一遍且实现不同（见 P1-3）。
- **A-4 订单耦合（P3）**：`prep.py` 依赖 `meta.py` 先跑出 `work/opts.json`，但 `meta.py` 又会整体重写这个文件；两步之间无契约声明，改任一步易踩坑。

### P0-1 · 技术面注释写死"空头排列"结论，永远输出同一句话

**位置**：`scripts/template2.html:259`


### P1-1 · `fetch2b.py` 吞异常后仍写盘，会制造永久数据空洞

**位置**：`scripts/fetch2b.py:92-131`

```python
try:
    df = pro.opt_daily(...)
except Exception as err:
    print("  ERR", ...)
    df = None            # ← 异常被吞，只打印
...
old = old[old["date"] < ms[0][0]]     # ← 无论前面成功与否，都截断旧数据
new = pd.concat([old, new], ...)
new.to_csv(RAW, ...)                  # ← 照常写回
```

**问题**：`opt_daily` 是按月分片拉取的。如果某个月分片失败（限频/网络抖动很常见），该月数据没进来，但写盘前 `old = old[old["date"] < ms[0][0]]` 已经把 `ms[0][0]` 之后的**全部旧数据丢掉**——包括那个失败的月份。结果是一段**永久空洞**，直到下次完整成功重跑才恢复。而这一次运行会"成功"退出（rc=0），`run_weekly` 继续往下跑，最终报告里的 PCR 序列会少一段而不自知。

对比：`fetch.py` / `fetch3.py` 的取数不捕获异常，失败就崩，反而是安全的。三个取数脚本失败模式不一致。

**修改建议**：加失败标记，异常时 `exit(非零)` 且**不写盘**；具体是循环内设 `fail=False`，`except` 里置 `True` 并 `break`，循环结束后 `if fail: sys.exit(2)`。另外加一道断言：新合成表的行数不得少于旧表行数（增量只会增不会减），不满足就拒绝写盘。

### P1-2 · `gen2.py` 中 `DIV[code]` 直接索引，人工文件缺 key 即整条管线崩溃

**位置**：`scripts/gen2.py:129` → `"div": DIV[code],`

**问题**：`DIV` 来自 `manual_inputs.json`。这份文件是**由 agent 每次联网检索后手写覆盖**的（提示词第 2 步），是最容易出错的一环：漏一个指数、拼错代码、写成 `null`，都会让 `gen2.py` 抛 `KeyError` 退出 → 管线 rc=1 → 当日**没有任何报告**。而提示词里同时写着"拿不到的数据不编造，保持原值"，说明"数据缺失"是**预期会发生的正常状态**，代码却没有为它做防御。

**修改建议**：`DIV.get(code)`，并在模板里把 `null` 显示为"—"（模板的 `fmt()` 已能把 null 渲染成"—"，`fmt(r.div,2)+'%'` 会变成"—%"，需顺手处理）。同类问题还有 `BOND10Y = float(MAN.get("bond10y", 0) or 0)`——缺 bond10y 时 ERP 会退化成纯盈利收益率（虚高 1.6pp 以上），建议改成显式失败并给出明确错误信息，而不是静默算错。

### P1-3 · "近5日"实为 6 个交易日、"近1月"实为约 21 个交易日、YTD 基准双写法

**位置**：`scripts/proc2.py:87-95`、`scripts/process.py:40-41`、`scripts/proc2.py:84`

**(a) 5 日 = 6 个交易日**
```python
def chg(back):
    i = len(vs) - 1 - back      # back=5 → vs[-6] → 6 个交易日前的份额
    return round(last - vs[i], 2), round((last / vs[i] - 1) * 100, 2)
```
实测：`asof=20261019`，`d5` 的分母日期是 `20261012`，中间隔了 10-13/14/15/16/19 共 **5 个交易日**，而 `vs[-6]` 与 `vs[-1]` 之间跨了 **6 个交易日的变化**。报告第 225 行表头写的是"近5日"，`views` 文案里也照抄成"近5日份额+46.7亿份"。同理 `d20 → vs[-21]`、`d60 → vs[-61]` 都多算一天。

**(b) `ret1m` 不是一个月**
```python
M1 = cfg.shift(ASOF, months=-1)
m1 = [r for r in daily if r["trade_date"] >= M1]
ret1m = close / m1[0]["close"] - 1
```
`m1[0]` 是"ASOF 往前一个月之后的第一天"，取的是那个点——ASOF=10-19、M1=09-19，`m1[0]` 落在 09-21 前后，与"近 1 个月"相差 1–2 个交易日。用一个区间起点当基准，语义上是"一个月零几天"。当前该字段未在报告表格中直接展示（只在 `views` 里可能被引用），但只要有人引用就会错。

**(c) YTD 基准两套写法**
- `process.py:36`：`prev = [r for r in daily if r["trade_date"] < YEAR + "0101"]` —— 正确，随年份滚动
- `proc2.py:84`：`y0 = [i for i, x in enumerate(ds) if x < "20260101"]` —— **写死年份**，2027 年仍恰好正确，2028 年起 ETF 份额 YTD 会错误地一直以 2026 年末为基准

**修改建议**：三个问题一次解决——把 `chg(back)` 统一改成按**交易日偏移**定义（`i = len(vs) - 1 - back` 时表头写"近 N+1 日"，或干脆改 `i = len(vs) - back` 让语义对齐表头），并在 `README` 里写明"近 N 日为 N 个交易日的区间变化"；`ret1m` 改成"距 ASOF 最近的不晚于 M1 的那个交易日收盘价"（即 `[r for r in daily if r["trade_date"] <= M1][-1]`）；`proc2.py` 的 `"20260101"` 改为 `ASOF[:4] + "0101"`，并抽成 `cfg` 里的公共函数供 `process.py` 复用。

### P2-2 · 人工观点段（views）与自动指标混写，数字对不上

**位置**：`data/manual_inputs.json` → `views` / `syn`，注入 `template2.html:437/455`

实测今日 10-19 报告的人工段落中，至少 3 处数字与管线计算结果**不一致**：

| 文案 | 实际计算值 | 差异 |
|---|---|---|
| 中证500 PE 分位 71.5%、PB 分位 69.1% | PE 71.5% ✓、PB **69.1%** ✓ | 一致（此项无误） |
| 创业板指"PE 分位 17.9% 仍处十年低位"、"隐含 ROE 14.1% 为五者最高" | PE 17.9% ✓、ROE 14.14% ✓ | 一致 |
| 沪深300 views 中"近 5 日份额 +46.7 亿份" | 实为 **6 个交易日**变化 | 见 P1-3 |
| 上证50 views "距 250 日高点回撤 -12.2% 也为五者最浅" | -12.2% ✓ | 一致 |

**核心问题不在个别数字，而在机制**：`views`/`syn` 是 agent 用 LLM 手写的中文段落，里面**大量复述自动指标**（PE 分位、PCR 分位、份额变化、回撤）。任何一次管线口径调整（比如把 5 日改成 5 个交易日），这些手写数字**不会自动跟着变**，而且没人会去逐个复核。今天侥幸都对，但这是长期必然出错的点。

**修改建议**（三选一，按成本排序）：
1. **低**：在 `views` 文案规范里明确"只写定性判断与外部观点，不写可计算的数值"，数值一律由表格承担。同时提示词加一条自检要求。
2. **中**：给 `views` 增加结构化字段（如 `{"text": "...", "refs": ["pe_pct","pcr.oi"]}`），由 `gen2` 在做模板注入时把 `{{pe_pct}}` 占位符替换成实际值。这样口径改了数字自动跟。
3. **高**：彻底拆分——`views` 只放机构引述与来源，指标性描述全部由 `gen2` 动态拼装。

### P2-3 · `manual_inputs.json` 的 `views`/`syn` 无时效校验，可能安静地旧一天

**问题**：`DATA.divAsof` 取自 `manual_inputs.json` 的 `asof`（当前 `20261013`），而 `views` 里的日期描述是 10-19。`template2.html:205` 把机构观点的"最近更新"显示成 `DATA.divAsof`：

```js
document.getElementById('viewasof').textContent=DATA.divAsof;
```

于是报告会在机构观点段落标注"最近更新：**2026-10-13**"，而正文讲的其实是 10-19 的盘面。**用一个字段兼做两件事**（股息率日期 vs 观点日期），两者节奏完全不同（股息率长期滞后、观点每天更新），这是明确的建模缺陷。

**修改建议**：`manual_inputs.json` 增加独立字段 `views_asof`（及 `syn_asof`），模板分别引用；`gen2` 在有值时才用，缺省回退到 `asof` 但标注"（沿用）"。

### P2-5 · `run_weekly.py` 无任何交付前自检

**现状**：`run_weekly.py` 只做"跑子进程 + 打印末 6 行 + 检查 rc"。跑完就 `print("完成")` 并 `exit(0)`（实测 20s 全通）。

**缺的检查**（都是实际发生过的故障模式）：
- 报告文件是否真的生成、大小是否合理（历史上的 `_latest` 时代曾出现空文件）
- `DATA.asof` 是否等于 `cfg.ASOF`（若某步拿到旧缓存日期，会生成错日的报告而 rc=0）
- 各数据源日期是否新鲜（`pcrAsof`、`bondDate`、`divAsof` 分别落后几天）

- ERP 序列是否为空（`yield10y_history.json` 缺失时 `DATA.erp=None`，模板直接跳过整个专题，**不报错**）

**修改建议**：在 `gen2` 之后加 `selfcheck()` 函数：读回 `work/data2.json` 与生成的 HTML，做上述 5 项断言，不通过则 `exit(3)` 并在 stdout 打印明确原因。这样"管线成功"和"报告合格"就不再是同一件事。

## 五、提示词合理性评估

### 现有 prompt 全文结构

四步流程（运行判断 → 更新人工数据 → 生成报告 → 自检与交付）+ 铁律 1 条 + 报告口径 4 条。

### P1-5 · 第 2 步与第 3 步顺序矛盾（prompt 层面的 P1）

**现状**：
- 第 2 步："联网查最新数据，更新 `manual_inputs.json` 里的三项…… ③ 机构对五只标的的最新观点 + 每只指数一句话解读"
- 第 3 步："运行 `run_weekly.py`"

**矛盾点**：第 2 步的 ③（`views`/`syn`）本质上**必须引用当天的管线指标**——事实上今天的文案里就充斥着 PE 分位 71.5%、PCR 0.774、份额 +46.7 亿份、回撤 -12.2% 这些**只有跑完管线才存在的数字**。按字面顺序执行，agent 要么用**前一天**的指标写今天的观点（静默错误），要么违反流程。实际执行显然走了后者（先跑管线、再重写、再单独重跑 `gen2`），但这个"实际流程"**完全没有写进 prompt**，全靠 agent 临场悟。

**修改建议**：把四步改为五步，把"跑管线"提到"写观点"之前：

```
第 2 步 · 更新可提前确定的人工项（股息率 + 10Y 及各自日期）
第 3 步 · 跑管线（拿到当日全部指标）
第 4 步 · 据【第 3 步输出的指标】重写 views/syn，然后单独重跑 gen2.py
第 5 步 · 自检与交付
```

并明确写"`views`/`syn` 中的每一个数字都必须来自本次管线输出，不得沿用上一日"，这正是 P2-2 的根治手段。

### P2-6 · 第 1 步"运行判断"的判定方式不可靠

**现状**："先看 `reports/` 里最新的 `index_val_report_*.html` 的数据日期。若它已等于'最近一个交易日'……本次跳过"。

**问题**：判定依赖"最新"的定义，但 prompt 没说按什么排序。实际 `reports/index_val_report_20261016.html` 的 mtime 是 **10-19 09:41**（比 `20261018` 晚，因为它被手动重跑过），按 mtime 取"最新"会拿到 10-16 那份，从而误判。

**修改建议**：明确"按**文件名中的日期**取最大值"，并直接读该文件内嵌的 `DATA.asof`（比标题文本可靠，标题是 JS 动态填的，静态值是"—"）。

### P2-7 · 第 4 步自检清单太薄，且写的是人眼能看的、不是机器能验的

**现状**："① 自检：报告能正常打开、图表都显示出来、'数据日期'等于最近一个交易日；② 展示报告文件，并总结四件事"。

**问题**：三项都是"看起来对"级别。而且第 ① 项本身有个坑——"数据日期"在 HTML 里是 `<b id="asof">—</b>`，**静态值是"—"**，由 JS 在运行时填充。用 grep 查会永远查到"—"，用浏览器截图在本机又不可用（无头浏览器截图不可用，这是环境限制）。真正可靠的验证对象是 `work/data2.json` 里的 `DATA.asof`。

**建议补充的自检项**（都是踩过的坑）：
- 读 `work/data2.json`，断言 `asof == 预期交易日`
- 分别报告 `pcrAsof` / `bondDate` / `divAsof` 与实际交易日的差距，**在交付文案里明说**（"PCR 数据为 10-19"、"股息率沿用 10-13"）
- 提取内联 JS 跑 `node --check`
- 正则统计 `getElementById('x')` 的引用（**注意必须用单引号**，用双引号正则会误判为 0）
- 断言 ERP 专题存在且 `erp.series.length > 2000`
- 断言章节顺序（基本面→资金面→情绪面→技术面→总结→附录）
- 断言免责声明存在

### P2-8 · 铁律只有 1 条，覆盖不到最常出错的场景

**现状**：`【铁律】1. 拿不到的数据不编造，保持原值。`——这条很到位，但只约束了"数据缺失"。

**没约束到的**（都实际发生过或高风险）：
- **不得用外部来源覆盖管线指标**（曾出现用搜索快照的中证官网陈旧点位去"校正" Tushare 收盘价的风险）
- **不得手改生成的 HTML**（目录重组期间曾出现两份报告并存）
- **观点段数字必须与管线一致**（见 P2-2）
- **`manual_inputs.json` 必须是合法 JSON**（现在是靠 agent 自觉，`gen2` 的 `json.load` 崩了会表现为"管线失败"，排查成本高）

**修改建议**：铁律扩到 4 条，并让 `cfg.load_manual()` 在解析失败时打印**文件路径与解析错误位置**。

### 做得好的地方（建议保留）

1. "拿不到的数据不编造，保持原值"——这条铁律非常正确，且与 `dividend` 长期沿用 10-13 的实际行为一致。
2. "10Y 收益率补齐失败不影响出报告"——与代码 `fetch_yield_tail.py` 恒 exit 0 完全对应，口径一致。
